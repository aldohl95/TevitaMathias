SaveMySeat

A ticketing back end for small venues that never sells the same ticket twice.

Tools and languages

Java, Spring Boot, PostgreSQL, Flyway, JWT, JUnit 5, Testcontainers, k6, Prometheus, Docker, GitHub Actions, Render, Netlify, React, TypeScript, Vite

Evidence

  • Live demo (front end on Netlify)
  • Live API docs (Render)
  • Source code on GitHub
  • The 50-thread concurrency test
  • Design decision records
  • Load test results
  • k6 load test scripts
  • Continuous integration workflow
The problem
When several people try to buy the last few tickets at the same moment, a simple check-then-save lets more than one of them succeed. For a venue that means refunds and unhappy customers. I wanted to build the part of a ticketing system where correctness matters most, and then prove it works.
My role
I was the only developer. I designed the database schema and migrations, the REST API, authentication, the hold and order logic, the tests, the load tests, and the CI workflow. I also built a React and TypeScript front end with registration, login, venue and event browsing, ticket holds, simulated payment, and order history, then deployed the back end in Docker on Render and the front end on Netlify.
Decisions I made
Buyers hold tickets for a short time before they pay, and a scheduled job releases expired holds each minute. Creating a hold locks the ticket tier row in PostgreSQL, so only one transaction at a time can read and change the remaining count.
My design record compares that lock with optimistic locking, serializable transactions on everything, and Redis as the source of truth. I kept PostgreSQL as the single source of truth because it is the simplest design that cannot oversell. Later I replaced a conditional SQL update I had planned with SELECT ... FOR UPDATE and recorded why.
Login uses short-lived access tokens and refresh tokens that rotate, and reusing an old refresh token is rejected. Asking for another organizer's event returns "not found", so people can't probe which IDs exist.
Results
An integration test runs against a real PostgreSQL database. It starts 50 threads that each try to hold one ticket on a 10-ticket tier, then checks that exactly 10 succeed, the tier shows 10 reserved, and 10 holds exist.
On my laptop, k6 measured about 2,700 hold requests per second against a single tier and about 4,350 per second spread across 21 tiers. The gap shows that the row lock is the limit on throughput. These are laptop numbers, not production benchmarks.
What is unfinished
Payment is a placeholder with no real Stripe integration yet. Login has no rate limiting, and each order covers one ticket tier. I removed an unused Redis setup because PostgreSQL is the source of truth. The live back end runs on Render's free tier, so the first request after it sleeps can take a minute. I listed these gaps in the project documentation instead of hiding them.

Task Mentor

A deployed team web app that connects students with mentors for short, task-based help.

Tools and languages

Java 21, Spring Boot, Spring Security, JWT, JPA, PostgreSQL, React, Vite, Docker, Render, Netlify

Evidence

  • Team source code on GitHub
The problem
Traditional mentorship is open-ended and hard to schedule. In Task Mentor, mentors publish a menu of specific, time-limited services such as a 30-minute resume review, and students book exactly the help they need.
My role
I was the project manager and a full-stack developer on a four-person team, and I wrote 61 of the repository's 92 commits. I ran our branch and pull-request workflow. I built the mentor search, the login and registration back end with JWT, the React login state and protected routes, the cross-origin (CORS) configuration, and the first batch of unit, integration, and security tests.
Decisions I made
Students and mentors see different features, so I added role-based access with protected routes in the React app, backed by JWT authentication in Spring Security. I put search in its own service and controller so the dashboard and the mentor browsing page can share it.
Results
Every core feature in the README is checked off: registration and login, student and mentor profiles, task offerings, mentor search with filters, and booking requests that mentors can accept or decline. We containerized the back end with Docker and deployed it on Render, with the front end on Netlify.
Late in the release I tracked down bugs that crossed the front end and back end, including CORS, routing, and redirect problems, and fixed them before the final version.

InterviewPrep CLI

A command-line tool that tracks coding interview practice and schedules reviews.

Tools and languages

Python 3.11, Click, Rich, platformdirs, pytest, Black, Ruff

Evidence

  • Source code on GitHub
  • Package on PyPI
  • Scheduling algorithm write-up
  • Automated tests
The problem
I was tracking practice problems across spreadsheets and notes. I wanted one place to log each attempt, see which patterns I struggle with, and know what to review today.
My role
I was the only developer. I wrote the specification, built every command, wrote the tests, and documented the project. I worked on feature branches and merged through pull requests.
Decisions I made
I wrote a simple review scheduler as a table of intervals based on how hard I found a problem and whether I needed help, instead of the SM-2 algorithm. It is easier to test and explain for one person's data, and I documented it before coding it.
Data is stored as JSON so it is easy to read and back up. Reviewing a problem creates a new attempt record instead of editing the old one, which keeps my history intact. Problem names act as identifiers, which I accepted for a single-user tool.
Results
The tool can add, list, view, edit, and delete problems, record reviews, show a progress dashboard, list what is due today with a streak counter, and import or export data as JSON. It has 42 automated tests and is published on PyPI as interviewprep-cli, so it installs with pip or pipx.
What I would improve next
Move storage to SQLite, separate a problem from its attempts, recalculate schedules when a problem is edited, add list filters, and add a continuous integration pipeline. This repository does not have one yet.

Service Request Tracker

A full-stack app for submitting, searching, and updating service requests.

Tools and languages

Java 17, Spring Boot, Maven, JUnit, React, Vite, JSON file storage

Evidence

  • Source code on GitHub
  • Unit and integration tests
The problem
A team needs one place to submit requests, find them by status, priority, requester, or keyword, discuss them, and see every change that was made.
My role
I built the Spring Boot back end in stages: the data models, service layer, REST controller, validation, combined search filters, partial updates, comments, and change history. I then connected a React front end.
Decisions I made
Requests are saved in a JSON file, so the app runs with no database setup. Updates use PATCH so a client can change only the status or priority. A search with no matches returns a clear message instead of an empty or null response.
Results
The back end has 76 automated tests, covering both unit and integration cases. Some of those tests were written with AI assistance, as my commit messages note.

More practice work, including coding exercises and small games, is on my GitHub repositories page.
